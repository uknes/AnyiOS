## Adopt next — ranked (five maximum)

1. **LLVM ld64.lld / llvm-objdump** — introduce an opt-in Linux + Windows CI fixture job that cross-links original ARM64 iOS `MH_EXECUTE`/`MH_DYLIB` using only project-authored C files and a **home-authored metadata-only** `libSystem.tbd`. Compare load commands and imports to the existing macOS oracle; do not claim this works until both link and our inspector tests pass. No Apple SDK contents redistributed.
2. **LIEF (test oracle only)** — pinned CI Python venv parses the exact same owned Mach-O artifact as our inspector; compare segments, import symbols, entry and dyld metadata. Do not make it a runtime library.
3. **SDL3** — create an optional host shell displaying an empty window and capturing keyboard/mouse/touch-like events on Windows x64/ARM64, without claiming UIKit implementation.
4. **GNUstep libobjc2 (separate ABI research)** — build MIT runtime in an isolated Windows proof, then verify the layout/calling convention of independently authored Objective-C metadata. Do not load a guest Apple ObjC object until ABI comparison passes.
5. **SPIRV-Tools** — introduce `spirv-val` into an optional owned shader fixture test; this can validate later graphics work but does not solve Metal/AIR decoding.

## Decision on SDK-free cross-linking

`ld64.lld` supports Mach-O targets outside macOS. An **original**, metadata-only TAPI `.tbd` shim containing solely the symbols/installation name we declare ourselves is worth testing. Feasibility is plausible, **not yet CI verified**; ld64.lld version, platform version, chained-fixup support and required `libSystem` metadata may reject the fixture. Never fetch/rebundle Apple SDK libraries. Use `llvm-objdump --macho --all-headers`, `llvm-readobj`, and optionally LIEF as independent fixture oracles.

## Thunking / runtime findings

MIT FEX documents guest→host thunk calls, explicit argument marshaling and host→guest callback transitions; MIT Box64 documents wrapped-library strategies. AnyiOS must **reimplement** the concepts through a versioned guest-ABI thunk interface, not import or copy either implementation. Existing native Windows ARM64 execution is in-process and needs isolation and Darwin SVC trapping before arbitrary guest use. Apple ARM64 reserves `x18`, and Apple variadic calling conventions differ from the Windows ARM64 ABI. ABI thunks must handle variadic arguments, sign/zero extension, pointer provenance, callbacks, stack alignment and nonvolatile register preservation. Reference: https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms and https://github.com/MicrosoftDocs/cpp-docs/blob/main/docs/build/arm64-windows-abi-conventions.md.

MIT libobjc2 and Apache Foundation/libdispatch are **source/API research candidates**, not prebuilt Apple iOS ARM64 binary-compatible replacements. The ABI, metadata, TLS and platform bindings have to be established independently; the Foundation tree may include files with separate notices.

## Graphics/AIR reality check

The required translation direction for a future Metal renderer is Metal/AIR→portable shader IR→Vulkan/SPIR-V or D3D12, **not** SPIR-V→MSL. SPIRV-Cross, glslang, SPIRV-Tools, Vulkan headers, DXVK and VMA do **not** supply a mature Metal-to-D3D12 translator. A publicly available AIR→SPIR-V alpha exists (metal2vulkan, LGPL-3.0), but its project explicitly calls it research-grade and no broad real-game conformance has been proven. **No mature, verified, permissively licensed drop-in AIR→SPIR-V or Metal→D3D12 translator was established in this survey.** Avoid integrating the alpha or assuming all AIR is interchangeable with generic LLVM bitcode. SDL3, Skia, FreeType and HarfBuzz can eventually back host windowing, 2D rendering, font rasterization and shaping for an independently developed CoreGraphics/CoreAnimation subset, but are not substitutes for UIKit/Metal ABI implementations.
